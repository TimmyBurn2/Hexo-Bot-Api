# HeXO Bot API

**Status: 0.5, generated from the reference server's contract.** The reference
server answers every operation in development; no deployment serves them yet.

## What this is

`openapi.yaml` is the surface a bot uses to play on a HeXO server: presence,
challenges, the public directory, and the account over HTTP, and each game on
its own websocket. Nothing server-internal leaks through, so another server can
answer this contract. The website's surface (sign-in, owners managing bots,
watching games) stays outside this file: it answers to browser sessions, not bot
tokens.

`openapi.yaml` and `examples/stream.ndjson` are generated by the reference
server's `pnpm spec:export`; they are never edited by hand.

## Words

A **ply** is one stone placed; a **turn** is one player's action. Both count from
zero: turn 0 is the origin stone at (0, 0), ply 0, and every later turn is two
plies. `x` owns turn 0, `o` turn 1.

## The loop

1. Get a bot token (`hxo_...`) from the owner's page on the website.
2. `PATCH /api/bot/account` to declare `about`, `version`, `repoUrl`, and the
   clocks you `accept`. The body is strict: an unknown key answers 400. A
   challenge outside `accepts` is refused for you.
3. `GET /api/bot/stream?open=1` and hold it open. The connection is the bot's
   presence, and `open=1` says it takes challenges and games; both end with it.
4. On `challenge`, accept or decline it. To challenge another bot,
   `POST /api/bot/challenge/{name}` with a fresh `requestId`; resending the same
   one is safe.
5. On `gameStart`, note the `gameId`, your `side`, and `engine`: dial
   `engine.socketUrl` as a websocket with `?token=` set to `engine.token`.
6. The engine session speaks htttx `basic_websocket` v1-alpha. A `setup` packet
   holds the stones before any turn; each `move_request` lists in `previous` the
   turns this connection has not seen, the opening included. Answer with a
   `move_response` of two placements, echoing `request_id`, or it is dropped. A
   bot playing here must support the `move_skips` and `request_id`
   capabilities. An illegal move forfeits.
7. To concede, `POST /api/bot/game/{gameId}/resign` with the game token.
8. On `gameFinish`, the game is over.

Reconnecting the stream replays every live game as `gameStart` with a fresh game
token; dial again and the new connection replaces the old one, then replays the
game in `previous`. A bot needs no state across connections.

## The opening

Every game begins with `openingPlies` stones the server places before either
player acts: 1, 3, 5, 7, or 9, the origin included, default 5. They land within
hex distance 2 of the origin, and an opening that leaves one side a threat is
redrawn whole. The first player turn is turn (`openingPlies` + 1) / 2, and it
places two stones like every turn after it.

## Engine schemas

`Coord`, `Board`, `PositionEvaluation`, `Move`, `MoveRequest`, and
`MoveResponse` are copied verbatim from [htttx-bot-api](https://github.com/hex-tic-tac-toe/htttx-bot-api) at commit
`37d2385`; `scripts/check-htttx.sh` diffs the vendored block against upstream.
They are published under htttx-bot-api's MIT License, whose notice is in `NOTICE`.
The engine session's packets are htttx `bws-v1-alpha` at the same commit.

Those schemas use axial `q,r` (+q right, +r top-right), and so does every
coordinate a bot sees.

## Examples

- [`examples/simple_bot.py`](examples/simple_bot.py): the loop above, with
  `websockets` as its one dependency. `choose_move` returns the free cells
  nearest the stones already placed; replace it with an engine and nothing else
  changes.
- [`examples/stream.ndjson`](examples/stream.ndjson): one line per event type.

## Linting

```
make lint          # Redocly + Spectral, both must report 0 errors
make check-htttx   # diff the vendored block against upstream (needs network)
make docs          # render dist/index.html
```

`make lint` reads `openapi.yaml`, `redocly.yaml`, `.redocly.lint-ignore.yaml`,
and `.spectral.yaml`, and nothing else. Beyond the npm registry `npx` fetches
the linters from, `make check-htttx` is the only target that reaches the
network.

## Rating

`rating` and `provisional` are server-local: the contract fixes their shape, an
integer and a boolean, and not how a server computes or anchors them.
